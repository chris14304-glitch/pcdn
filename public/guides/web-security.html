Introduction: Why Web Security Matters

Web security encompasses the practices, technologies, and strategies used to protect websites, web applications, and web services from threats and attacks. In an era where businesses, governments, and individuals depend on web-based systems for everything from banking to healthcare, the stakes of getting security wrong have never been higher.

For developers, web security is a professional responsibility. A single vulnerability in your application can expose millions of user records, lead to devastating financial losses, and destroy the trust your organization has built over years. For users, understanding web security helps you recognize phishing attempts, evaluate whether a site is trustworthy, and take proactive steps to protect your own data.

Key Principle

Security is not a feature you bolt on at the end. It must be integrated into every phase of the software development lifecycle -- from architecture design and code review to deployment and ongoing monitoring.

The threat landscape evolves constantly. Attackers use automated tools to scan millions of websites for known weaknesses, and new vulnerability classes emerge as web technologies advance. Staying informed and following established security frameworks is the most effective defense.

OWASP Top 10 Overview

The Open Web Application Security Project (OWASP) maintains a regularly updated list of the ten most critical web application security risks. This list serves as a standard awareness document and a starting point for securing your applications. Below is an overview of each category.

1. Injection Attacks

Injection flaws occur when an attacker sends untrusted data to an interpreter as part of a command or query. The most well-known form is SQL injection, where malicious SQL statements are inserted into input fields to manipulate the database. Command injection similarly allows attackers to execute arbitrary operating system commands on the server.

SQL Injection Example (Vulnerable)SQL
-- User input: ' OR '1'='1' --
SELECT * FROM users
WHERE username = '' OR '1'='1' --'
AND password = 'anything';

-- This bypasses authentication entirely
Parameterized Query (Safe)JavaScript
// Always use parameterized queries to prevent injection
const result = await db.query(
  'SELECT * FROM users WHERE username = $1 AND password = $2',
  [username, hashedPassword]
);

The primary defense against injection is to never trust user input. Use parameterized queries (prepared statements), input validation, and stored procedures. Employ the principle of least privilege for your database accounts so that even a successful injection limits the damage an attacker can do.

2. Broken Authentication

Broken authentication vulnerabilities allow attackers to compromise passwords, session tokens, or authentication keys to assume the identity of other users. Common weaknesses include permitting brute-force attacks, using default credentials, poor session management, and exposing session IDs in URLs.

Mitigation strategies include implementing multi-factor authentication (MFA), enforcing strong password policies, using secure session management with proper timeout and invalidation, and rate-limiting login attempts to prevent credential stuffing.

3. Sensitive Data Exposure

When applications fail to adequately protect sensitive data such as financial records, healthcare information, or personal identifiers, attackers can steal or modify that data. This category covers failures like transmitting data in cleartext, using weak cryptographic algorithms, or storing passwords without hashing.

Common Mistake

Never store passwords in plaintext or use weak hashing algorithms like MD5 or SHA-1. Always use purpose-built password hashing functions such as bcrypt or Argon2, which include salting and configurable work factors.

4. XML External Entities (XXE)

XXE attacks target applications that parse XML input. Attackers can exploit vulnerable XML processors to read internal files on the server, perform server-side request forgery (SSRF), execute remote code, or launch denial-of-service attacks. The root cause is that many older XML parsers allow the declaration of external entities by default.

The fix is straightforward: disable external entity processing in your XML parser configuration, use less complex data formats like JSON where possible, and validate and sanitize all XML input against a strict schema.

5. Broken Access Control

Access control enforces policies so users cannot act outside their intended permissions. When these controls fail, attackers can access other users' accounts, view sensitive files, modify access rights, or elevate privileges. Common examples include insecure direct object references (IDOR), missing function-level access checks, and metadata manipulation (such as tampering with JWT tokens).

Enforce access control on the server side, deny by default, implement role-based access control (RBAC), log access control failures, and rate-limit API access to minimize automated abuse.

6. Security Misconfiguration

This is the most commonly encountered issue. It happens when security settings are not defined, implemented, or maintained properly. Examples include leaving default accounts active, exposing stack traces or verbose error messages, leaving unnecessary services or ports open, and failing to set appropriate security headers.

Regular hardening processes, automated configuration audits, removing unused features and frameworks, and maintaining a repeatable deployment process are all essential to preventing misconfigurations.

7. Cross-Site Scripting (XSS)

XSS flaws occur when an application includes untrusted data in a web page without proper validation or escaping, allowing attackers to execute scripts in the victim's browser. There are three main types: Stored XSS (malicious script is permanently saved on the target server), Reflected XSS (script is reflected off the server in error messages or search results), and DOM-based XSS (the vulnerability exists in client-side code).

XSS PreventionJavaScript
// DANGEROUS: Directly inserting user input into DOM
element.innerHTML = userInput;

// SAFE: Use textContent to prevent script execution
element.textContent = userInput;

// SAFE: Use a sanitization library for rich content
import DOMPurify from 'dompurify';
element.innerHTML = DOMPurify.sanitize(userInput);

8. Insecure Deserialization

Insecure deserialization often leads to remote code execution. Even when it does not result in code execution, it can be used for replay attacks, injection attacks, and privilege escalation. Applications that deserialize data from untrusted sources without validation are at risk. Avoid accepting serialized objects from untrusted sources, implement integrity checks, enforce strict type constraints, and isolate deserialization code in low-privilege environments.

9. Using Components with Known Vulnerabilities

Modern applications rely heavily on open-source libraries and frameworks. If any component in your stack has a known vulnerability, attackers can exploit it. This is especially dangerous because automated scanners make it trivial to discover which libraries a site uses and whether they are outdated.

Maintain an inventory of all client-side and server-side dependencies, continuously monitor sources like the National Vulnerability Database (NVD) for alerts, and apply patches promptly. Use tools like npm audit, Dependabot, or Snyk to automate vulnerability detection.

10. Insufficient Logging and Monitoring

Without adequate logging and monitoring, breaches go undetected. Studies show the average time to detect a breach often exceeds 200 days. Ensure that all login attempts, access control failures, and server-side input validation failures are logged with sufficient context. Establish effective monitoring and alerting so that suspicious activities are detected and responded to in a timely fashion. Build or adopt an incident response and recovery plan.

HTTPS and TLS/SSL

HTTPS (HTTP Secure) uses TLS (Transport Layer Security) to encrypt the communication between a user's browser and the web server. TLS is the successor to SSL, which is now deprecated. When you visit a site over HTTPS, three things happen: the server proves its identity via a certificate issued by a trusted Certificate Authority (CA), a symmetric encryption key is negotiated via a handshake, and all subsequent data is encrypted in transit.

Without HTTPS, any data sent between the browser and server can be intercepted and read by anyone on the network path, including login credentials, personal data, and session cookies. Modern browsers flag HTTP sites as "Not Secure" to warn users.

Mixed Content Warnings

If your HTTPS page loads resources (scripts, images, stylesheets) over plain HTTP, browsers will block or warn about "mixed content." This undermines the security of HTTPS because those unencrypted resources can be tampered with by an attacker. Always ensure all resources are loaded over HTTPS.

Free certificate authorities like Let's Encrypt have made HTTPS accessible to everyone. There is no longer a valid reason to serve any website over plain HTTP. Configure your server to redirect all HTTP traffic to HTTPS and enable HSTS (HTTP Strict-Transport-Security) to ensure browsers always use the secure connection.

Security Headers

HTTP security headers instruct the browser to enable (or restrict) certain behaviors, providing a critical layer of defense. Here are the most important ones to configure:

  • Content-Security-Policy (CSP) -- Defines approved sources for content, preventing XSS and data injection attacks. This is the single most powerful header for mitigating client-side attacks.
  • Strict-Transport-Security (HSTS) -- Forces browsers to only use HTTPS for your domain, preventing protocol downgrade attacks and cookie hijacking.
  • X-Frame-Options -- Prevents your site from being embedded in iframes, defending against clickjacking attacks. Values: DENY or SAMEORIGIN.
  • X-Content-Type-Options -- Set to nosniff to prevent browsers from MIME-sniffing a response away from the declared content type, blocking certain attack vectors.
  • Referrer-Policy -- Controls how much referrer information is sent with requests. Use strict-origin-when-cross-origin or no-referrer to minimize data leakage.
Recommended Security HeadersHTTP
Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: https:;
Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
X-Frame-Options: DENY
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(), microphone=(), geolocation=()

Authentication Best Practices

Authentication is the process of verifying that someone is who they claim to be. Getting it right is critical because a broken authentication system can give attackers unrestricted access to your entire application.

Password Hashing

Passwords must never be stored in plaintext. Instead, use a slow, salted hashing algorithm designed specifically for passwords. The two recommended choices are:

  • bcrypt -- A well-established algorithm that includes a configurable cost factor. Widely supported across all languages and platforms.
  • Argon2 -- The winner of the Password Hashing Competition. Provides memory-hard hashing that resists GPU-based brute force attacks. Recommended for new projects.
Password Hashing with bcryptJavaScript (Node.js)
const bcrypt = require('bcrypt');
const SALT_ROUNDS = 12;

// Hashing a password
const hash = await bcrypt.hash(plaintextPassword, SALT_ROUNDS);

// Verifying a password
const isMatch = await bcrypt.compare(plaintextPassword, storedHash);

Session Management

Sessions track authenticated users across requests. Best practices include generating cryptographically random session IDs, setting the HttpOnly, Secure, and SameSite flags on session cookies, implementing idle and absolute timeouts, regenerating the session ID after login to prevent session fixation, and invalidating sessions on logout.

OAuth and OpenID Connect

OAuth 2.0 is an authorization framework that allows third-party applications to access a user's resources without exposing their credentials. OpenID Connect (OIDC) is an identity layer built on top of OAuth 2.0 that provides authentication. Together, they power the "Sign in with Google/GitHub/etc." flows that are both more secure and more convenient than managing passwords yourself. When implementing OAuth, always validate redirect URIs, use the state parameter to prevent CSRF, and store tokens securely.

CORS: Cross-Origin Resource Sharing

CORS is a browser security mechanism that restricts how a web page from one origin can request resources from a different origin. Without CORS, the same-origin policy would block all cross-origin requests, which is secure but overly restrictive for modern web applications that rely on APIs hosted on different domains.

The server indicates which origins are permitted via the Access-Control-Allow-Origin header. Common misconfigurations include setting this header to * (allowing any origin) while also allowing credentials, reflecting the requesting origin without validation, or exposing sensitive headers unnecessarily.

Secure CORS ConfigurationJavaScript (Express)
const cors = require('cors');

const allowedOrigins = [
  'https://app.example.com',
  'https://admin.example.com'
];

app.use(cors({
  origin: function(origin, callback) {
    if (!origin || allowedOrigins.includes(origin)) {
      callback(null, true);
    } else {
      callback(new Error('Not allowed by CORS'));
    }
  },
  credentials: true,
  methods: ['GET', 'POST', 'PUT', 'DELETE'],
  allowedHeaders: ['Content-Type', 'Authorization']
}));

Content Security Policy in Depth

Content Security Policy (CSP) is the most effective client-side defense against XSS and data injection attacks. It works by specifying exactly which sources of content the browser should trust for each resource type. Any content that does not match the policy is blocked.

A CSP is delivered via the Content-Security-Policy HTTP header. Key directives include:

  • default-src -- Fallback for all resource types not explicitly specified.
  • script-src -- Controls where JavaScript can be loaded from. Avoid 'unsafe-inline' and 'unsafe-eval' whenever possible.
  • style-src -- Controls stylesheet sources. Use nonces or hashes instead of 'unsafe-inline' for maximum security.
  • img-src, font-src, connect-src -- Control images, fonts, and fetch/XHR endpoints respectively.
  • frame-ancestors -- Modern replacement for X-Frame-Options; controls who can embed your page.
  • report-uri / report-to -- Sends violation reports to a specified endpoint for monitoring.
CSP with NoncesHTTP + HTML
// HTTP Header (server generates unique nonce per request)
Content-Security-Policy: script-src 'nonce-abc123def456';

<!-- HTML: Only scripts with the matching nonce will execute -->
<script nonce="abc123def456">
  // This script runs
</script>

<script>
  // This script is BLOCKED (no nonce)
</script>
CSP Tip

Start with a report-only policy (Content-Security-Policy-Report-Only) to discover what your application loads before enforcing. This lets you build a tight policy without accidentally breaking functionality.

API Security

APIs are the backbone of modern web applications and present a large attack surface. Securing them requires a layered approach covering authentication, authorization, input validation, and abuse prevention.

  • Authentication tokens -- Use short-lived JWTs or opaque tokens. Store tokens in HttpOnly cookies rather than localStorage to prevent XSS-based theft. Implement token refresh mechanisms to minimize the impact of compromised tokens.
  • Rate limiting -- Protect against brute-force attacks and abuse by limiting the number of requests per client per time window. Use token bucket or sliding window algorithms. Return 429 Too Many Requests with a Retry-After header.
  • Input validation -- Validate all input on the server side regardless of client-side validation. Use schema validation libraries (like Joi, Zod, or JSON Schema) to enforce types, ranges, lengths, and formats. Reject unexpected fields.
Rate Limiting MiddlewareJavaScript (Express)
const rateLimit = require('express-rate-limit');

const apiLimiter = rateLimit({
  windowMs: 15 * 60 * 1000, // 15 minutes
  max: 100,                       // 100 requests per window
  standardHeaders: true,
  legacyHeaders: false,
  message: { error: 'Too many requests, please try again later.' }
});

app.use('/api/', apiLimiter);

Supply Chain Attacks

Supply chain attacks target the software dependencies and build tools that applications rely on, rather than the application itself. These attacks are particularly insidious because developers implicitly trust the packages they install.

Key attack vectors include:

  • Compromised npm packages -- An attacker gains access to a maintainer's account (via credential theft or social engineering) and publishes a malicious version of a popular package. All downstream projects that update to the new version are compromised.
  • Typosquatting -- Attackers publish packages with names very similar to popular ones (e.g., lodahs instead of lodash). Developers who make a typo during installation unknowingly install malware.
  • Dependency confusion -- Attackers publish a public package with the same name as an internal private package but with a higher version number. Build systems configured to check public registries first will pull the malicious public version.
Defense Measures

Use lockfiles (package-lock.json, yarn.lock) to pin dependency versions. Run npm audit regularly. Consider using tools like Socket.dev that analyze package behavior, not just known CVEs. Scope your private packages to an organization and configure your registry properly to prevent dependency confusion.

Web Application Firewalls (WAF)

A Web Application Firewall sits between users and your web server, inspecting HTTP traffic and blocking malicious requests before they reach your application. WAFs use a combination of signature-based detection (matching known attack patterns), anomaly detection (flagging unusual traffic), and configurable rules to filter threats.

A WAF can help defend against common attacks like SQL injection, XSS, file inclusion, and DDoS (distributed denial of service). However, a WAF is not a substitute for secure coding practices. It is a defense-in-depth layer -- an additional safety net that catches attacks that slip through other controls. Popular WAF solutions include AWS WAF, Cloudflare WAF, and ModSecurity (open source).

When configuring a WAF, start in monitoring mode to learn your application's normal traffic patterns before enabling blocking rules. Regularly review and update rulesets, and avoid overly permissive rules that provide a false sense of security.

Security Scanning Tools

Security testing should be an ongoing part of your development process, not a one-time event. Automated scanning tools help identify vulnerabilities before attackers do.

  • OWASP ZAP (Zed Attack Proxy) -- A free, open-source penetration testing tool for finding vulnerabilities in web applications. It can perform automated scans, intercept and modify requests, and fuzz inputs. Ideal for integration into CI/CD pipelines.
  • Burp Suite -- A comprehensive platform for web application security testing. The Professional edition includes an advanced scanner, an intruder tool for automated attacks, and a repeater for manual testing. Widely used by security professionals.
  • Static analyzers (SAST) -- Tools like Semgrep, SonarQube, and CodeQL analyze source code for security vulnerabilities without executing it. They catch issues early in the development process, including hardcoded secrets, insecure patterns, and injection vulnerabilities.
  • Dynamic analyzers (DAST) -- Tools that test running applications by sending crafted requests and analyzing responses. OWASP ZAP and Burp Suite fall into this category.
  • Software Composition Analysis (SCA) -- Tools like Snyk, Dependabot, and npm audit scan your dependencies for known vulnerabilities and license compliance issues.
Shift Left

Integrate security scanning into your CI/CD pipeline so that every pull request is automatically checked for vulnerabilities. This "shift left" approach catches issues early when they are cheapest to fix and prevents insecure code from reaching production.
